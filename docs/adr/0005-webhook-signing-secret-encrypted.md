# Webhook signing secrets are stored encrypted, not hashed

## Context and Problem Statement

SPEC §5 listed `webhook_endpoints.secret_hash` and `previous_secret_hash`, by analogy with client
secrets, and issue #5 built the columns as listed. Standard Webhooks (SPEC §8.2, PLAN §3 row 11)
signs every delivery with HMAC-SHA256 keyed by the secret itself, so the dispatcher needs the
secret each time it sends. A hash can check a secret that someone presents; it cannot sign. Issue
#28 asks how the secret is stored and how it is rotated, before any code writes an endpoint.

## Decision Drivers

* The dispatcher must be able to sign every delivery, including a retry a day later and both
  signatures during a rotation overlap.
* A database dump, a preview branch or a query that leaks a row must not yield a usable secret on
  its own. The nightly dumps leave the provider (SPEC §21.2).
* One mechanism for every secret the system has to use again. Provider credentials need the same
  thing in Phase 2 (`provider_links.credentials_enc`).
* Consumers verify with the Standard Webhooks libraries, unchanged.
* Migrations are expand/contract (SPEC §11 item 12).

## Considered Options

* Encrypt the secret with the envelope encryption of SPEC §5 (chosen)
* Keep only a hash
* Store nothing: derive each secret from a master key and the endpoint id
* Asymmetric signatures (Standard Webhooks `v1a`, Ed25519)
* Store the secret in plaintext

## Decision Outcome

Chosen: **encrypt the secret with the envelope encryption of SPEC §5**, because it is the only
option that lets the dispatcher sign, keeps a leaked row useless without a key held outside the
database, and lets that key be rotated without any customer changing anything.

* **Storage.** `webhook_endpoints.secret_enc` holds the current secret and `previous_secret_enc`
  the one a rotation replaced, each as one opaque text value: a per-value data key (AES-256-GCM,
  WebCrypto) wrapped by the region's master key from Workers secrets, with a format version and
  the master key's id, bound to its organisation, its row and the kind of secret it is.
  `packages/db` treats it as text.
* **The secret.** `whsec_` followed by 32 random bytes in base64, generated by the API and shown
  once, at creation and at rotation. Once means once: the response kept for idempotent replays
  (SPEC §1) is stored without the secret, and a replay returns it without the secret. Otherwise
  `idempotency_keys` would hold a readable copy of what `secret_enc` encrypts.
* **Rotation.** The replaced secret keeps signing for 24 hours. During that time each delivery
  carries both signatures in `webhook-signature`, separated by a space, which the Standard Webhooks
  libraries accept (they split the header on spaces and pass if any signature matches). Rotating
  again inside the overlap replaces the previous secret, so there are never more than two. A
  rotation is one `UPDATE` that stores the new ciphertext and moves the old one to
  `previous_secret_enc` unopened. That is why a value is bound to its kind and not to its column:
  bound to the column, the old secret would have to be decrypted and sealed again on every
  rotation, a second place where the plaintext exists.
* **Migration.** `0002` is the expand step: it adds the two `*_enc` columns and gives `secret_hash`
  an empty default, so that new code stops writing the hash while a previous release's inserts
  keep working. `secret_hash` keeps `NOT NULL`: `squawk` bans dropping it, and a reader of the old
  shape never meets a `NULL` this way. The contract step (drop both `*_hash` columns, make
  `secret_enc` `NOT NULL`) is a later release, issue #46.
* **Not built here.** Sealing and opening a value, the master key and its runbook belong to the
  first issue that writes one of these columns (the webhook endpoints). There is one
  implementation, in `packages/core`, shared with provider credentials.

### Consequences

* Good: the dispatcher can sign, and a database copy alone signs nothing.
* Good: provider credentials and signing secrets share one scheme, one key hierarchy and one
  rotation runbook.
* Good: the master key's id travels with each value, so the master key can be rotated without a
  customer noticing.
* Bad: the secret is recoverable by whoever holds both the database and the region's master key.
  The master key must be escrowed (SPEC §21.4); losing it leaves every endpoint unable to sign
  until a replacement key is installed and the endpoint's secret is rotated. One rotation is
  enough: the unreadable secret becomes the previous one, and a previous secret that will not open
  is left out of the signature (SPEC §8.2), so the new secret signs alone from the first delivery.
* Bad: a caller that loses the response to a rotation cannot read that secret again. It has to
  rotate a second time, which ends the overlap of the secret its consumer still holds. Keeping the
  secret in the stored response would avoid that, at the price of a second copy in the database.
* Bad: two dead columns stay in the table until issue #46.
* Neutral: `secret_enc` is nullable until issue #46. An endpoint whose current secret is missing or
  will not open fails its delivery; it is never sent unsigned (SPEC §8.2).
* Neutral: an expired previous secret stays in the row, as ciphertext, until the next rotation
  overwrites it. It is never used. Clearing it sooner would need a cross-organisation job and can
  join the retention cron later.

### Confirmation

* `packages/db/src/webhook-endpoints.int.test.ts`: a row with only `secret_enc` inserts, the
  previous release's insert (only `secret_hash`) still does, and a rotation is one statement.
* The redaction helper masks `whsec_…` wherever it appears (`packages/core/src/redact.ts`).
* The issues that build the endpoints and the dispatcher add the tests that no response other
  than create and rotate returns a secret, that a same-key replay of either returns none and
  `idempotency_keys.response` holds none, and that a signature verifies with a Standard Webhooks
  library, including both signatures during the overlap (SPEC §11 items 1 and 1a).

## Pros and Cons of the Options

### Encrypt with the envelope encryption of SPEC §5

* Good, because the dispatcher gets the secret back and nothing else does without the master key.
* Good, because Phase 2 needs the same mechanism for provider credentials anyway.
* Bad, because there is now a key whose loss or leak matters, with an escrow and a rotation runbook.

### Keep only a hash

* Good, because nothing recoverable is stored.
* Bad, because HMAC cannot be computed from a hash of its key: no delivery could be signed.

### Store nothing: derive each secret from a master key and the endpoint id

* Good, because there is no ciphertext to protect or migrate.
* Bad, because rotating the master key would change every customer's signing secret at once, so
  in practice the master key could never be rotated.
* Bad, because a per-endpoint rotation still needs stored state (a counter and the overlap expiry).

### Asymmetric signatures (Standard Webhooks `v1a`, Ed25519)

* Good, because a consumer holds only a public key, so a leak on their side forges nothing.
* Bad, because the private key still has to be stored, which is the same problem.
* Bad, because the symmetric scheme is what consumers' libraries use by default.
* Neutral, because it can be added later as a second signature on the same delivery without
  changing how secrets are stored.

### Store the secret in plaintext

* Good, because it is the least code.
* Bad, because every backup, dump and preview branch would carry live signing secrets.
